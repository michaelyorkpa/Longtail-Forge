# Operational Security

This document defines the minimum operational-security contract for the current Longtail Forge private-preview line. It is an operator baseline, not a security certification, penetration-test result, or claim that an internet deployment is perfectly safe.

## Production logs and request correlation

When `LONGTAIL_ENV=production`, process output is newline-delimited JSON. Every record has `timestamp`, `level`, and a stable `event`. HTTP completion records also contain a server-generated `requestId`, method, status code, and duration in milliseconds. The same opaque ID is returned in the `X-Request-ID` response header so an operator can correlate one response with its log record. Client-supplied request IDs are not trusted or reused. As of 0.33.27.3, this correlation value comes from the central opaque UUIDv4 authority; it remains non-secret and carries no ordering semantics.

Production logging uses a strict field allowlist. It deliberately omits request paths and query strings, request/response bodies, headers, cookies, session IDs, bearer tokens, passwords, secret values, database and storage paths, private record contents, and raw error messages or stacks. The production console bridge converts legacy console writes into safe classified records without copying their arguments. Application errors use a safe error type only. Do not weaken this boundary to make debugging easier; reproduce privately with sanitized diagnostics instead.

As of 0.33.23.1, a server-side 500-class failure writes one `http.request.failed` diagnostic under the response's request ID. Its additional allowlisted context is classification-only: `errorType`, a bounded `errorStack` containing sanitized function names rather than messages or paths, `routeClass`, `actorState`, and `workspaceState`. It never records the URL, route parameters, user/workspace IDs, exception message, raw stack, SQL, filesystem path, or request data. Expected client errors do not create this failure diagnostic. Internal and versioned API error bodies carry the matching request ID; unexpected browser documents show it in their HTML fallback.

For support, ask only for the displayed Request ID, approximate time, and attempted action. Match that opaque value exactly to one `http.request.failed` diagnostic; a separate `http.request.completed` record is normal and is not another failure diagnostic. Do not request passwords, bearer URLs, cookies, bodies, private record text, or raw protected IDs. The full support workflow, response contract, and in-process `503` versus proxy-maintenance boundary are in [http-errors.md](http-errors.md).

Collect stdout and stderr through the service manager or container runtime, restrict log access to operators, set an explicit retention period, and protect exported logs as potentially sensitive operational data even though the application redacts its structured fields.

## Public-demo runtime identity

Public-demo behavior is a default-off framework profile, not a hostname convention. `DEMO_MODE=true` is accepted only for the exact production demo origin under the Compose deployment identity, an immutable `main` release, the self-hosted installation mode, disabled Support View, and a regular, narrowly permissioned `.longtail-demo-data.json` marker in the configured data root whose contract and target identify `rt-ltf-demo`. Application and worker startup verify that marker before database, Files, scanner, or worker initialization. Public-demo-prefixed credentials, seed controls, reset metadata, or login-assistance settings are rejected whenever demo mode is off.

The framework capability catalog is authoritative for public-demo server enforcement. Demo mode returns the stable safe `public_demo_capability_disabled` denial before authorization or persistence for installation/workspace administration and deletion, new account/workspace/role-assignment paths, API keys and every `/api/v1` request, backups and exports, private feeds, Support View, and Secure Notes catalog transitions. Registered module actions, public API endpoints/scopes, and jobs must declare a known capability; undeclared or unknown contributions fail closed while demo mode is active. Currently absent integration, invitation, installation-backup, workspace import/export, restore, and extension-administration capabilities are recorded as disabled so later contributions cannot become implicitly available. Browser filtering is explanatory only; the service/request boundary remains authoritative.

The protected marker also carries exactly six UUID user IDs selected by the reviewed seed contract; runtime enforcement tests only that set and never infers ownership from usernames, labels, email domains, or roles. Marked visitors may authenticate, expire normally, and log out, but self-service and administrator-on-user credential/profile takeover, recovery, forced-password, managed-session, membership/account retirement, and API-key paths fail with one safe `public_demo_identity_immutable` response. Login never rehashes a marked visitor credential, and a marked visitor cannot enter account-export recovery. The separately protected Super Administrator is never marked and retains its ordinary credential-recovery lifecycle.

The unauthenticated `GET /api/public-demo/accounts` catalog is a narrow exception for the six intentionally public visitor credentials. It is no-store and available only while the exact demo profile is active; normal mode returns generic not-found. Its fixed source projection includes readable role/scope guidance, representative fictional records, useful actions, and expected denials, but no internal IDs, live directory or account state, marker data, operator identity, or private credential. The browser constructs the helper with text-only DOM APIs after validating all six entries. Selecting or filling credentials performs no login request and creates no session; only the unchanged `/api/login` submit reaches durable throttling and real/dummy password verification, preserving generic failures and non-enumeration.

Normal installations preserve their existing authorization, login markup, and focus behavior when demo mode is false or the optional catalog is unavailable or malformed. Operator-only host backup, reset, restore, and recovery commands remain outside the visitor request surface. A regenerated demo candidate contains no sessions, so cookies from the prior data root fail on their next request after reset. Runtime diagnostics disclose the profile state, stable capability classifications, and the configured perimeter limits plus their active/inactive state. They never return counters, client/session bucket keys, public credentials, private paths, marker contents, release recovery material, operator details, or the private Super Admin.

## Public-demo durable growth, input, and query budgets

The 60-second perimeter bounds request rate; the durable budget bounds admitted work for the rest of the current hourly baseline. For only the six marker-owned visitor identities, successful authenticated mutations consume one unit per operation plus declared bulk or generated-row units. Each visitor may consume 120 units and the shared workspace may consume 600. Reservation and both ceilings are checked in one serialized database transaction before module work; a response failure releases the reservation, while success survives app restart. The reviewed external reset replaces the database with an empty verified baseline, so no in-process timer or browser counter is authoritative.

Input admission caps an array at 50 items, an ordinary field at 8 KiB, a rich-text/body field at 32 KiB, an object at 100 fields, nesting at eight levels, and the parsed payload at 2,000 nodes. Query admission caps the raw query at 2,048 bytes, fields at 32, list values at 20, ordinary query text at 512 bytes, Search text at 200 bytes, page size at 100, offset at 1,000, and page number at 40. The existing 128 KiB perimeter and route-specific body limits remain independent outer ceilings.

Every current authenticated browser API mutation and read template has a stable catalog operation ID. Fixed browser documents such as the authenticated Dashboard do not consume durable mutation or query budget and pass to the ordinary protected-view authorization boundary; the budget catalog remains fail closed for `/api` operations. Unknown future API routes fail with `public_demo_budget_undeclared` for marked visitors until reviewed; normal deployments bypass the catalog. Denials use stable generic codes and fixed recovery hints, reach no module persistence, and expose no submitted content or budget usage. Runtime diagnostics expose only fixed limits, enabled state, and catalog size, never visitor/workspace counters or identities.

## Cross-role editable-content safety

Public-demo content uses ordinary module validation, permission-scoped reads, the framework Markdown service, text-only browser insertion, safe server-rendered HTML fields, and the standing CSP; there is no demo-only renderer. Tasks and Lists preserve markup-shaped values as literal text. Notes stores Markdown source, rejects script-capable elements, event attributes, and scriptable schemes with a fixed non-reflective 400 response, and renders saved/detail preview HTML through the same server adapter. Files Markdown preview consumes that framework renderer too.

The shared URL policy permits reviewed web/mail schemes and safe app-relative paths but rejects protocol-relative and slash-backslash network destinations. The public-demo rich-content classifier covers both `body_markdown` and `bodyMarkdown` at the configured 32 KiB ceiling; oversize failures expose no submitted content. The reviewed field and browser-sink inventory plus the contributor checklist are maintained in [editable-content-safety.md](editable-content-safety.md). Any new editable renderer, HTML sink, URL scheme, or content field must update that inventory and pass the cross-role hostile-input regression before it is available to visitors.

## Public-demo outbound and infrastructure isolation

The exact public demo has no application-owned outbound channel. The capability catalog explicitly disables email, webhooks, arbitrary URL fetches, integrations, analytics, feedback, and interest capture. Those surfaces are currently absent; their catalog entries reserve fail-closed identities rather than introducing placeholder implementations. Direct requests and registered jobs receive the same stable capability denial, and a future undeclared action, endpoint, scope, job, or runtime setting is unavailable while demo mode is active. Security, request, and reset records stay in the bounded operator-only logging contracts described here; they are operational evidence and are never forwarded to a product-analytics provider.

Application denial is backed by the root-owned `longtail-forge-public-demo-isolation` helper. The exact host uses the external Docker network `longtail-forge-public-demo-internal`, created as a dedicated non-masquerading IPv4 bridge with interface `ltf-demo0`, the loopback-only resolver `127.0.0.1`, and the dedicated volume `longtail-forge-public-demo-data`. Docker's internal-network flag is excluded because the supported live engine suppresses the required loopback publication for that topology. Instead, the helper installs and checks first-position firewall chains that allow established/related return traffic for the realized `127.0.0.1:8001` Caddy path, allow new host-input only to the reviewed ClamAV gateway/port, and drop every other new host-input or forwarded connection. Its keys-only container proof recognizes the Dockerfile-owned `NODE_ENV=production` value but no provider or undeclared application configuration. Its live smoke requires the application to be the network's sole peer, proves ClamAV remains reachable by its literal reviewed address, and proves external name resolution plus host-service and public-network probes cannot connect.

The same smoke checks the container's exact two persistent mounts, read-only root filesystem, disabled Docker auto-restart policy, bounded host-local container logs, fixed SQLite/Files/backup paths, local storage provider, inline worker, disabled Support View, and a narrow environment-name allowlist. S3 credentials, unsafe runtime overrides, provider tokens, analytics/feedback settings, and future undeclared `LONGTAIL_*` settings make public-demo startup or lifecycle proof fail closed. The deployment helper enforces the firewall before scanner preflight and repeats the complete smoke after startup; the hourly reset re-enforces it before mutation and repeats the smoke after restart. A host reboot leaves the demo stopped until a protected lifecycle operation re-establishes the firewall and starts it, so Docker cannot recreate a reachable container before isolation. `DEMO_MODE=false` retains ordinary supported self-hosted and local development behavior.

As of 0.33.31.14, `npm run demo:release-candidate:smoke -- --container` assembles the twelve authoritative demo contract owners, controlled runtime artifact, and native container lifecycle against one source revision. The released [redacted profile](public-demo-compose.env.example) and [operator runbook](public-demo-operator-runbook.md) contain no credential value. This repository proof does not claim live-host isolation, recovery, or publication acceptance.

## Public-demo perimeter threat model and response

This boundary protects one small shared demonstration service, not a general multi-tenant rate-limiting platform. The bounded threats are credential stuffing against the six published accounts, contention when several visitors use one account, request or mutation floods, repeated expensive Search reads, interference with the hourly reset, and database/disk pressure from large bodies or excessive evidence. Distributed attacks above one Node process and one Caddy edge, volumetric denial of service before Caddy, and hosted multi-node enforcement remain infrastructure/provider concerns.

The controls are deliberately layered:

| Threat | Control | Safe evidence |
| --- | --- | --- |
| Credential stuffing and password-hash pressure | The existing database-backed authentication throttle remains authoritative for failed login/account and trusted-IP lockouts. Its global/per-IP verification admission limits run before expensive password verification. The perimeter does not replace or reset this durable state. | Login and new lockout security events include the safe request ID; responses stay generic and non-enumerating. |
| Broad request flood | A 60-second in-process global bucket allows 2,400 non-probe requests, and a trusted-client-IP bucket allows 600. `/healthz`, `/readyz`, and `/api/app-info` do not consume capacity. | The first crossing for a bucket/window writes one `public_demo.perimeter.blocked` operational record and one forced `security.public_demo.perimeter_limited` event. |
| Shared-account and NAT contention | Mutations allow 120 requests per hashed browser-session bucket per minute. Login always stays IP-keyed so a forged cookie cannot split its budget. Six ordinary visitor sessions behind one IP therefore receive independent mutation capacity beneath the generous 600-request client ceiling. | Evidence records the request ID, limit class, method class, route class, window, limit, and retry interval, never the session or bucket key. |
| Expensive Search reads | Search allows 60 requests per hashed browser-session bucket per minute, with trusted client IP as the anonymous fallback. | The same bounded crossing event uses the `search` scope. |
| Oversized or malformed bodies | Public-demo requests declaring more than 128 KiB fail in application middleware before route parsing. Streaming JSON readers retain their own byte ceiling for absent or false declarations. Stock Caddy caps every proxied body at 8 MB, so extreme/chunked input is stopped before Node; in the tested Caddy 2.11 topology that edge abort intentionally uses the existing correlated generic maintenance `503`, while the tighter application boundary returns the canonical correlated `413`. Files ingress remains separately denied before upload parsing. | Neither layer logs bodies. The Caddy-only rejection appears only in redacted edge evidence; an application `413` has the same request ID in the response and app completion log. |
| Reset interference and retained pressure | Deployment and reset share the existing host lock, the scheduler has no catch-up behavior, reset logs are bounded, and the perimeter caps work admitted while the app is available. Caddy access evidence omits paths/headers, masks client addresses, deletes `Set-Cookie`, and relies on bounded service-manager retention. | Reset correlation/operation IDs remain in the root-only reset JSONL; request IDs remain in edge/application/security evidence. Correlate by exact ID, time window, and immutable release identity, never by submitted content. |

The defaults were selected with `npm run demo:perimeter:probe`. The 2026-08-07 reference run proved exact pass/block boundaries at 600 client requests, 2,400 global requests, 120 session mutations, and 60 session searches, plus 60 parallel mutations from six sessions sharing one client IP. Observed p95 latency was below 1 ms for sequential limiter probes and 32.49 ms for the parallel shared-NAT case on the reference workstation; those timings are diagnostic observations, not a production SLA. Re-run the probe after changing a limit or proxy/runtime version, review normal demo traffic first, and change one threshold at a time. All `LONGTAIL_PUBLIC_DEMO_*` overrides are rejected unless the exact demo profile is active. There is no hostname bypass and no setting that disables the perimeter while demo mode remains active.

Caddy generates `{http.request.uuid}`, overwrites upstream `X-Request-ID`, and writes the same value as `request_id` in its JSON access record. Node accepts that UUID only when the socket peer matches the explicit `TRUST_PROXY` allowlist; direct clients, untrusted peers, malformed values, and arbitrary inbound request IDs receive a new Node UUID. Edge records replace the complete URI with `REDACTED`, remove request headers and response `Set-Cookie`, and mask IPv4/IPv6 client addresses to `/24` and `/56`. Application logs retain their strict allowlist. Authentication, capability-denial, and perimeter security events store the request ID only through the security metadata allowlist. Capability denials never add route paths or submitted values.

For the public demo, retain Caddy/application service logs for no more than seven days unless an active incident requires a separately protected evidence hold. Security events follow the workspace audit-retention setting. The reset scheduler retains its root-only 336-record/seven-day JSONL contract. Service-manager or container log caps must be configured on the host; application code does not make an unbounded local access-log file. Keep all three sources operator-only.

When a perimeter alert fires:

1. Copy only the request ID, event time, limit scope, status, and immutable release identity into the restricted incident record.
2. Find the exact `request_id` in Caddy service logs, then the exact `requestId` in application logs and the protected security-event view. For reset overlap, compare the protected reset correlation/operation record in the same time window; do not copy reset stdout/stderr.
3. Confirm the trusted-proxy chain and effective client classification before changing limits. A shared `/24` in edge logs is supporting context, not a user identity.
4. If abuse is active, contain at the public edge or remove public traffic. Do not disable durable authentication throttling, relax proxy trust, publish port 8001, or switch off the reset lock/safety checks.
5. Preserve a narrow protected evidence export if needed, rotate any actually exposed credential, restore service, and re-run `npm run demo:perimeter:probe` plus the Caddy smoke before reopening traffic.
6. Delete temporary evidence at incident close and return to the normal retention window. Never add passwords, submitted content, raw sessions, bearer URLs, analytics identifiers, or complete request paths to make correlation easier.

## Support View identity and event boundary

Support View is an install-level security capability and remains disabled unless `LONGTAIL_SUPPORT_VIEW_ENABLED=true`. The dedicated `support_view.enter` permission is granted only to the installation Super Admin role; ordinary Workspace Administrators do not receive it. The administrator entry page requires an active target user/workspace selected through readable labels, current-password reauthentication, bounded reason/reference text, and explicit confirmation of the read-only warning and visible expiry.

The authenticated administrator remains the actor. Durable state and request context carry a separate effective user and exactly one effective workspace. Current-password verification uses the shared trusted-client-IP/account throttle, and entry plus exit rotate the opaque browser session ID. Expiry, runtime disablement, authority loss, user or membership deactivation, and workspace deactivation terminate the support state immediately; restoration creates a new normal session only for a still-active actor with a valid active workspace.

`support_sessions` and `support_view_events` retain bounded reason/reference text, actor/effective/workspace attribution, start/expiry/end timestamps, safe outcome classifications, request IDs, and stable route/action/reason identifiers. They exclude credentials, password hashes, cookies, browser session IDs, query strings, request/response bodies, secure content, and arbitrary payload metadata. The same safe action attribution is emitted through the structured operational logger. Runtime diagnostics disclose only whether the install gate is enabled. A normal authorized Super Admin can filter the append-only review surface and export at most 1,000 safe rows; ended sessions and their events are retained for 365 days. Support View itself cannot open the target catalog, audit API/page, or export.

After live support-session validation, one central request gate replaces authorization identity with the target's live user/workspace context, permits only declared read-safe GET/HEAD actions, and denies every other method before protected routers execute. Sensitive and undeclared reads return ordinary not-found. The sensitive catalog includes credential/token/recovery and auth-factor surfaces, exports/backups, billing/payment or integration-secret configuration, security/audit/session administration, raw file content, and secure Notes/catalog state. A newly added protected read must be declared and pass the release-gate source audit; modules cannot create an override for central mutation denial.

Browser presentation is intentionally redundant with that server policy: every protected page carries a persistent, non-dismissible banner naming the viewed user/workspace and the actor, showing remaining time, explaining unavailable changes and protected surfaces, and offering an immediate **End Support View** action. Write-looking controls are disabled, including controls added after render, but this is clarity rather than authorization; protected data must be excluded before rendering. End returns to a normalized same-origin safe path and restores focus to the landing heading. Settings **Log Out** is the other permitted lifecycle action: it ends the attributed support state and expires authentication without restoring an administrator session.

## Secure Notes catalog boundaries

Catalog policy uses the same effective-security result for explicit secure notes, direct secure catalogs, inherited ancestors, and fail-closed transition or malformed-hierarchy states. Effectively secure bodies and revisions stay encrypted at rest. Normal Files, activity, notifications, Search, resume/Workbench, public API, exports, generic provider catalogs, and Support View omit the record rather than returning a partial title or count. Enabling effective security removes existing normal Search documents, notification/subscription rows, and resume-state rows for the affected notes; read-time policy checks still fail closed if cleanup is interrupted. Internal events and audit records omit titles, bodies, excerpts, encryption fields, and secret metadata. Do not add a Notes consumer that reads `security_mode` directly; declare it in `protectedContentConsumers` and call the Notes policy assertion.

Catalog enable, retry, and downgrade require `notes.secure.manage` plus Library management. Security is effective as soon as a versioned transition is claimed. A failed or interrupted transition remains protected and operator-visible; it never falls back to normal. Downgrade additionally requires current-password reauthentication and exact catalog/action/count confirmation. Moving a note or subtree out of inherited protection preserves explicit security and writes a separate safe audit action rather than downgrading silently.

## Private calendar feed bearer URLs

As of 0.33.22.9, `GET /feeds/calendar/:token.ics` remains a sessionless, read-only authentication surface. As of `0.33.22.9.3`, new and rotated links use `GET /feeds/calendar/:token/:calendarName.ics` so filename-based clients can show the subscription's path-safe friendly name; the token-only route remains supported. The complete URL is a bearer secret: anyone who receives it may request the owner's currently permitted Tasks calendar for its workspace. Do not put it in tickets, chat, screenshots, analytics, proxy access logs, browser telemetry, or monitoring labels. Production request logging omits paths, queries, headers, cookies, and bodies; lifecycle security events contain only safe create/rotate/revoke/automatic-invalidation classifications and reason/scope metadata. Every upstream proxy and observability layer needs the same path-redaction rule.

The database stores independently identified named active-or-revoked rows. Each is bound to its creator and one Workspace, Client, or Project entitlement scope. Project scope is available to every workspace type; Client scope is accepted only in Business workspaces, while Personal and Family workspaces remain Client-free. Storage contains only a random selector and SHA-256 digest of a separate high-entropy secret. The raw URL is returned once on creation or owner rotation. Workspace administrators can list safe workspace metadata and revoke any row but cannot mint for another user, recover another URL, or rotate another owner's credential. Every public read rechecks the owner, membership, workspace type, Tasks module, target lifecycle, and exact live `tasks.view` scope before provider dispatch. Canonical lifecycle reconciliation and startup repair update durable status, while read-time rejection remains authoritative if repair fails.

Malformed, unknown, rotated-away, revoked, inaccessible, and invalid-scope tokens receive the same `404` body. Framework dispatch exposes only an immutable secret-free subscription descriptor. Tasks reauthorizes that exact Workspace/Client/Project scope, applies the ceiling in its Task and recurrence-template queries, and then intersects those rows with current record permissions. Client scope follows the Project's current Client parent; moved out-of-scope recurrence instances become title-free cancellations rather than content. An authorized scope with no matching Tasks returns a valid empty calendar, while lost scope authority remains a generic rejection. Requests use the trusted client-IP resolver and durable IP-only sensitive-endpoint throttle. Successful and rejected reads consume the budget; `429` includes `Retry-After`, while valid responses remain `text/calendar`, `private, no-store`, with a 900-second refresh hint.

As of 0.33.32.37, this entire framework edge is checked. The post-authentication permission identity is deliberately separate from browser sessions and contains no browser-session credential or Support View state. Selected database rows, normalized scopes, lifecycle payloads/results, provider context, and public responses use explicit contracts; lifecycle JSON remains unknown until service narrowing, and management routes require an authenticated active-workspace session. These checks do not relax the identical-failure rule or permit bearer material in a descriptor, response, audit event, or diagnostic.

The `/api/private-feeds/calendar-subscriptions` collection/item routes are browser-session protected and require `workspace_settings.manage`. Settings -> Admin -> Modules -> Calendar is their sole management surface; User Settings and the retired singular lifecycle routes cannot manage subscriptions. Create always binds the new row to the authenticated actor. Business workspaces may submit Workspace, Client, or Project scope; Personal and Family workspaces expose Workspace and Project, discard Client options, and receive a server rejection for forged Client scope. Owner-only rotation returns a replacement URL once, and safe list reads expose only lifecycle, owner, scope, and effective owner-timezone metadata—never URLs, selectors, digests, or token prefixes. Workspace administrators may revoke another owner's active row but cannot rotate it or recover its secret. Manual Revoke emits the lifecycle security event and deletes the credential row, which makes the bearer URL unknown immediately and removes the list entry. Rows already revoked by automatic eligibility reconciliation remain deletable through a separately classified cleanup action. The Calendar page remains available for listing, revocation, and deletion while Tasks is disabled; create and rotate fail closed until Tasks and the owner's required live scope are active.
## Health and readiness

The unauthenticated probes are intentionally minimal and always set `Cache-Control: no-store`:

| Probe | Success | Failure meaning |
| --- | --- | --- |
| `GET /healthz` | `200 {"status":"ok"}` | No response means the HTTP process or route is unavailable. It does not prove database or worker readiness. |
| `GET /readyz` | `200 {"status":"ready"}` | `503 {"status":"not_ready"}` means the database runtime, current migration set, or configured worker is not ready. |

`/readyz` requires a writable database with its expected runtime safety controls, an applied and checksum-valid current migration set, and a live worker. Inline mode uses the in-process runner state. SQLite separate-worker mode uses the heartbeat on the existing single-worker lock file; a missing or stale heartbeat is not ready. Disabled worker mode is not ready. Neither response identifies the failing component or exposes versions, paths, worker IDs, errors, secrets, or configuration details. Use correlated private logs and protected runtime diagnostics to investigate.

Reverse-proxy or orchestrator checks should use `/healthz` for process liveness and `/readyz` for traffic eligibility. Do not use `/healthz` alone to decide that a deployment can safely receive user traffic.

## Dependency and repository scanning plan

Before friends-and-family invitations, the repository owner must review and enable the capabilities available for the repository and plan:

1. Enable Dependabot alerts and scheduled dependency-update pull requests for npm. Review lockfile changes, release notes, transitive changes, install scripts, licenses, and the full release gate before merging; do not auto-merge dependency updates solely because they are automated.
2. Run `npm audit` in CI against the committed lockfile and review the complete report. Define a documented severity threshold for the preview gate, but still triage lower-severity and unreachable findings instead of treating the threshold as proof of safety.
3. Enable dependency review on pull requests when the repository plan supports it, so newly introduced vulnerable dependencies and material license changes are visible before merge.
4. Enable CodeQL code scanning for JavaScript/TypeScript on pull requests, the default branch, and a schedule. Triage results against the actual runtime and preserve suppressions with a concrete rationale and review date.
5. Enable secret scanning and push protection where available. Keep user-level push protection enabled, review every bypass, rotate/revoke a real credential immediately if one is committed, and remove it from history only after rotation. Continue local review because scanning recognizes patterns and cannot detect every secret.
6. Keep GitHub private vulnerability reporting enabled, subscribe the maintainer to security alerts, and test that the repository's **Report a vulnerability** action opens the private form.

These tools identify known advisories and detectable patterns. A clean dependency, code, or secret scan does not prove the application is secure, does not validate deployment configuration, and does not replace threat review, permission/workspace regressions, manual review, incident readiness, or tested restoration.

## Minimum private-preview incident response

For a suspected compromise, credential exposure, private-data disclosure, or actively exploitable vulnerability:

1. **Receive privately and start a restricted incident record.** Record time, reporter, affected version/deployment, observed indicators, and the current incident owner. Do not copy secrets or private content into tickets or chat.
2. **Contain.** Pause invitations and deployments. If exploitation may be active, remove public traffic at the reverse proxy or stop the app while preserving data. Disable affected accounts, revoke relevant sessions/API keys, and rotate exposed runtime secrets or external credentials. Do not destroy the only evidence while containing.
3. **Preserve and scope.** Preserve access-controlled logs, configuration classifications, database/storage snapshots, and relevant timestamps. Use request IDs to correlate activity. Determine affected users, workspaces, records, versions, and time window without broadening access to private content.
4. **Eradicate and recover.** Fix the root cause on a private branch, add a regression, review adjacent trust boundaries, rotate/revoke again where necessary, restore only from a known-good backup, apply migrations, and prove `/readyz`, permission/security gates, and targeted user workflows before returning traffic.
5. **Communicate privately.** Notify affected preview participants promptly with confirmed facts, required actions, data-impact scope, and the next update time. Avoid unsupported certainty. Coordinate disclosure with a private vulnerability reporter.
6. **Review.** Record the timeline, root cause, controls that worked or failed, follow-up owners, and completion evidence. Update this procedure and the pre-invitation checklist when the incident exposes a gap.

The tested baseline recovery capability and its limits are defined in [Baseline Backup and Restore](backup-restore.md). Do not claim recovery readiness unless the exact deployment has a recently inspected off-host archive, separately protected Secure Notes key recovery where required, recorded retention/access ownership, and a successful representative restore drill.

## Manual security review before invitations

The maintainer must complete and date one manual review immediately before the first invitation and repeat it after a material security, deployment, authentication, permission, storage, or recovery change. This review is paired with [Private Preview Readiness](private-preview-readiness.md), which owns the invitation gate and participant/account/feedback checklist. Invitations remain blocked unless every applicable item passes or a documented risk decision explicitly defers the preview:

Use [Reference Internet Deployment](internet-deployment.md) as the authoritative direct-Caddy or bounded Nginx/WireGuard/Caddy topology and operator procedure for the proxy-specific checks below.

- 0.33.16 security hardening and the reference TLS-proxy closeout are complete on the exact candidate version.
- The supported 0.33.17 deployment is reproducible, secrets and data paths have restricted permissions, and the Node listener is not directly public.
- Backup and restore from 0.33.17 have been tested end to end on representative data; the protected backup location, retention, access, and restore owner are recorded.
- `npm run closeout`, `npm run check`, `npm run test:permissions`, SQLite integrity, the focused security regressions, and the reference-proxy manual review pass on the candidate.
- `/healthz`, `/readyz`, production JSON logs, `X-Request-ID` correlation, and readiness failure behavior are verified without secret-bearing output.
- The deferred live HTTPS/proxy session review is recorded for the current candidate when applicable: public sign-in, authenticated refresh/navigation, workspace switching, logout/relogin, cookie persistence, and HTTP-to-HTTPS redirect behavior must be exercised against the real edge; local Caddy smokes are supplementary only.
- Login flood controls are reviewed on the exact candidate: application pre-verification admission stays enabled with explicit global/per-trusted-IP bounds, durable failure throttling remains enabled, and the bounded Nginx topology validates its `$binary_remote_addr` `/api/login` limit and generic `429` without trusting forwarded input. A direct-Caddy deployment records that no repository-owned proxy limiter exists and relies on the independently tested application controls.
- Dependabot/dependency review, vulnerability scanning, CodeQL, secret scanning/push protection, and private vulnerability reporting are reviewed and enabled where available; every open alert has a recorded disposition.
- The incident owner can execute containment, session/API-key revocation, secret rotation, evidence preservation, participant communication, restoration, and rollback without inventing steps during an incident.
- Known limitations and low-stakes-data guidance are included in the invitation; the preview makes no certification, perfect-security, uptime, or durability promise.

Record the reviewer, candidate version/commit, date, evidence links or command outputs, unresolved risks, and the invite/no-invite decision in a private operational record. Do not commit secrets, private incident evidence, participant data, or scan exports to this repository.
