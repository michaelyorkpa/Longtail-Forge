# Backup and Restore Operator Guide

[Baseline Backup and Restore](backup-restore.md) is the authoritative command and archive contract. Read it before operating on live data; this page is the release-operations entry point.

Every deployment and upgrade is backup-first. Docker Compose is the sole supported production/self-hosted recovery path. Hold ordinary public traffic, stop the Compose app, create a whole-instance archive containing the SQLite database and local Files state, supply the separately protected Secure Notes recovery-key backup when encrypted Notes exist, inspect both the archive and sidecar before replacing anything, and keep the backup outside the live data volume and public paths.

Restore is destructive and must replace database and Files state from the same verified archive. After restore, start without public traffic, require database integrity and migration identity, `/readyz`, the expected `/api/app-info` version and release identity, representative login/File/Secure Notes checks, and operator audit evidence before reopening the selected TLS edge.

The GitHub deployment helper follows this contract but does not make backups automatic in the product. Operators still own protected off-host copies, retention, recovery-key custody, observation periods, and representative restore drills. Never discard the only proven restore point during a release. The private-preview invitation gate in [Private Preview Readiness](private-preview-readiness.md) requires a tested restore before access is granted.

The exact `rt-ltf-demo` Compose reset helper follows the same backup-first boundary and shares one exclusive host lock with deploy and rollback. It asserts the maintenance curtain, stops and proves every SQLite user quiescent, creates and inspects the whole-instance archive, and only then swaps the matched database-and-Files baseline on the same filesystem. WAL/SHM sidecars move only while stopped. If activation, restart, readiness, identity, session invalidation, or representative role proof fails, the helper restores the retained prior database-and-Files unit and re-proves it; an unverified recovery leaves maintenance active and preserves evidence. This guarded manual reset is not a scheduler or a substitute for protected off-host backups.

For an interrupted Secure Notes catalog transition, do not edit catalog policy or encrypted rows directly. Keep traffic restricted if the failure followed a restore or key/configuration change, verify the separately protected Secure Notes key material and `/readyz`, then open Settings -> Admin -> Modules -> Notes with an account that has Manage Secure Notes and Manage Notes Library. The catalog remains effective-secure in `securing` or recovery-needed state. Review the safe preflight counts and blocker code, correct the operational cause, and use Retry Security; the versioned job resumes without exposing partially converted content. After completion, verify the catalog is stable, representative authorized reads work, normal Search/Files/notifications do not contain the protected note, `PRAGMA integrity_check;` returns `ok`, and the safe requested/completed audit records exist. Restore the whole database and Files archive plus the matching Secure Notes recovery key only when retry cannot be made safe; never decrypt or clear transition columns manually.
